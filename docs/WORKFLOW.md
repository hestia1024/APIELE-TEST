# 共同开发与发布

克隆本仓库后，把仓库目录作为 Codex 项目打开。Codex 会读取根目录 `AGENTS.md`；换电脑、换协作者或开新对话都按同一规则执行。规则依赖代理遵守，独立点击其他客户端的推送/部署按钮不受本脚本控制。

## 一次正常开发

1. 告诉 Codex 要改什么。Codex 先运行 `python workflow.py prepare`，报告当前版本、远端比较、拉取前后 Diff：版本范围、新增提交、改动文件类型及增删行数。Codex 阅读代码差异后，用中文概括关键变化和对本次任务的影响；无更新也明确提示。
2. Codex 编写代码，做相关验证，并记录需求、决策、修改和验证结果。
3. Codex 提示开发完成和待发布文件；没有发布指令时就停在这里。
4. 你或协作者明确说“发布本次修改到服务器”。Codex 用下面的命令提交指定文件、推送 GitHub、部署同一提交。
5. 看到提交号、GitHub 推送成功、服务器网站和数据库检查通过，才表示整次发布完成。

```powershell
python workflow.py release --message "说明本次修改" --files app/main.py docs/conversations/本次会话.md
```

`--files` 必须逐个列出审查过的文件，可包含删除文件；不接受整个目录。不自动提交已有暂存区或本次无关文件。Git 提交身份使用各自本机配置，不冒用别人的身份。

开发期间有人推送，发布检查会停止；同步后重新检查和验证，不静默合并。推送与部署之间按顺序执行；GitHub 推送失败时不会上传服务器。首次克隆需设置当前 main 跟踪 origin/main；常规 clone 默认已设置。

## 协作者首次接手

1. 克隆仓库并在 Codex 打开仓库目录，阅读本文件和 `PROJECT_CONTEXT.md`。
2. 配置自己的 GitHub 凭据（有仓库写入权限），以及 `git config user.name`、`git config user.email`。
3. 复制 `.env.example` 为 `.env`，线下取得已授权的服务器和数据库凭据；首次 SSH 连接核对指纹。
4. 按 README 启动本地 SSH 隧道和网站；数据库仍是共享开发库，双方可看到彼此的测试记录。
5. 开发和发布都遵守同一入口；同一时间只安排一人发布，当前简单部署脚本不支持多人并发发布。

## 聊天、操作和知识留在仓库

| 文件 | 内容 |
|---|---|
| `AGENTS.md` | 每次对话执行的规则及明确发布门槛 |
| `docs/PROJECT_CONTEXT.md` | 已确认需求、技术栈、数据库/部署结构、后续工作 |
| `docs/OPERATIONS.md` | 运行、排错、GitHub 认证阻碍和结果边界 |
| `docs/conversations/*.md` | 每次会话可共享的聊天文本、需求决策、操作及验证结果 |

公开仓库中保存脱敏文本和可接手的信息。真实密码、私钥、原始工具日志和含连接凭据的图片不上传。截图原图以占位说明代替，不能把没有图片的归档称作所有附件完整备份。

可读到本机 Codex JSONL 会话文件时，运行以下导出器；`--source` 使用各自电脑实际路径，不需要共享整个 Codex 配置目录：

```powershell
python tools/export_chat.py --source "本机会话.jsonl" --output "docs/conversations/日期-会话ID-transcript.md"
```

导出器仅处理用户/助手可见文本，排除内部推理、系统消息和工具原始输出，替换本机凭据；仍须检查变更。只能导出文件中实际存在的历史，不能恢复已缺失的逐字聊天。没有可读 JSONL 时写明“会话摘要”，记录原始需求、决策、操作、测试和阻碍，不冒充逐字归档。

每次提交只包含提交前已记录的对话；提交后的新消息、部署结果在下次记录更新时纳入。仓库文档帮助新 Codex 接手，但不等于把原 Codex 会话界面自动同步给协作者。

## 故障处理

- 拉取遇到本地修改或历史分叉：保留现场，说明冲突/差异，由当前用户决定处理方式。
- GitHub 认证/推送失败：不部署；先在本机完成 GitHub 登录和权限配置。已存在的本地提交保留，不重复生成相同提交。
- GitHub 已推送、部署失败：明确报告该状态。修复部署条件后，可用原提交执行 `python deploy.py --revision 完整提交号`，这是明确发布授权内的重试，仍遵守两次上限。
- 容器启动后检查失败：按 `OPERATIONS.md` 查看服务日志，不自动宣称发布成功。
- 同一问题两次尝试无结果：停止该路径，告知已尝试的操作、剩余阻碍和需要用户做的动作。

## 开源调研（2026-10-23）

| 项目 | 已确认情况 | 借鉴及适用性 |
|---|---|---|
| [Invoke](https://github.com/pyinvoke/invoke) | Python 任务执行工具；仓库未归档，2026-04-07 有推送；含 tests、integration、sites 文档；BSD-2-Clause | 可借鉴明确任务入口、命令失败即停止；当前流程用标准库 subprocess 即可，无需新增任务框架 |
| [Fabric](https://github.com/fabric/fabric) | Python SSH 远程执行/部署工具；仓库未归档，2026-04-10 有推送；含 tests、integration、sites 文档；BSD-2-Clause | 可借鉴连接/部署阶段划分；现有 Windows OpenSSH 已验证，切换会增加 SSH/Python 依赖集成成本 |

结论：借鉴流程，继续使用现有 Python、Git 和 OpenSSH。不复制第三方代码、不引入新框架。维护证据仅表示仓库状态和最近推送，不代表已逐项评估其发布质量。
